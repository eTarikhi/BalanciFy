# Release gates — owner, evidence, lead time and preparation

All statuses are **BLOCKED** until acceptable evidence exists and an authorized reviewer approves it. Planning lead times below are estimates for scheduling only; validate them with the provider, certifying lab, reviewer, and release owner. No signing, certification, independent review, VEX, release, rollback, or field acceptance is claimed by this checklist.

| Gate | Owner (role) | Evidence required to clear | Indicative lead time | What can be prepared now | Status |
|---|---|---|---|---|---|
| Driver signing and certification / WHCP | Release engineering + Windows driver owner | Enrolled organization/Partner Center account; accepted attestation-signed package or required WHCP/HLK package; signer identity and timestamp; submission receipt and approval; reproducible hashes matching the release candidate; supported Windows/architecture coverage. | Provider- and route-dependent; reserve 4–12+ weeks for enrollment, review, and iteration; confirm with Microsoft/CA before committing a date. | Confirm legal entity and enrollment owner; inventory hardware IDs/INF/catalog/SBOM; verify reproducible build and PE/HVCI flags; prepare test results and signing request; document certificate custody and renewal/incident procedures. Never put production keys in the repository or disposable test VM. | **BLOCKED — no approved signature/certification evidence supplied.** |
| Independent security review | Security lead + independent reviewer | Written scope and threat model; source commit and dependency inventory; cryptographic protocol review; IPC/ACL/admin-boundary review; driver memory/ownership/IOCTL review; findings with severity, remediation, and signed/dated closure report. | Planning estimate 2–6 weeks after scope and stable review package; depends on reviewer capacity and findings. | Assemble architecture and data-flow diagrams, trust boundaries, threat model, ADRs, security-sensitive code map, CI/SBOM results, fuzz/test corpus, known limitations, and an immutable review SHA. Prepare a finding-response tracker and remediation budget. | **BLOCKED — no independent report supplied.** |
| Reviewed VEX | Product security owner + SBOM/VEX reviewer | Per-release VEX bound to exact SBOM/package hashes; vulnerability identifiers, product status, justification and impact; citations/evidence for each non-affected/fixed/under-investigation claim; schema validation and reviewer approval. | Planning estimate 1–3 weeks for first reviewed release after SBOM and vulnerability triage are ready; recurring per release. | Generate and validate SPDX sidecars; lock package hashes; map direct/transitive dependencies to advisories; prepare a VEX draft with no unsupported “not affected” claims; define review and update SLA. A draft is not a reviewed VEX. | **BLOCKED — CI SBOM validation is not VEX review.** |
| Release and rollback readiness | Release manager + installer/service owners + support | Signed, immutable offline bundle; SBOM/VEX and provenance; supported OS/architecture matrix; clean install/upgrade/uninstall; failure injection and rollback journal; backup/restore; route/service/adapter/firewall/file residue checks; release notes, support and incident contacts; go/no-go approval. | Planning estimate 2–4 weeks after candidate is feature-frozen; longer if clean-machine or rollback defects are found. | Define release candidate SHA and artifact naming; draft release notes and support policy; identify clean x64/ARM64 VM templates; prepare offline bundle manifest, rollback scenarios, upgrade matrix, and acceptance evidence directory. | Field observations and operational readiness | Product owner + SRE/support + pilot customer | Approved pilot scope and consent; deployment/configuration records; real-device/driver/relay versions; telemetry/privacy review; uptime, crash, failover, support and uninstall evidence; incident log; user feedback; documented exit/rollback criteria. | Planning estimate 4–12 weeks for a meaningful controlled pilot; actual duration depends on usage and incident rates. | Identify pilot cohort and owner; define success/failure metrics, privacy minimization, consent, support contacts, escalation path, and safe rollback; prepare redacted incident and observation templates. Do not characterize lab tests as field observations. | **BLOCKED — no pilot or field data supplied.** |

## Gate review rules

1. Record the tested commit, artifact hashes, environment, commands, timestamps, owner, and reviewer with each evidence packet.
2. Keep CI/build evidence separate from installed runtime, hardware, external approval, and field evidence.
3. A gate remains BLOCKED when its evidence is absent, incomplete, unsigned, unreviewed, or tied to a different artifact hash.
4. Do not use production signing credentials or keys in this workspace or a disposable VM. Keep credential handling inside the approved signing provider's secure workflow.
