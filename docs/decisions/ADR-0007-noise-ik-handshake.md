# ADR-0007 — session establishment: a first-party `Noise_IK` handshake

Status: accepted · Date: 2026-10-19 · Builds on: ADR-0006 (the AEAD) · Related:
§9.2, §4.8, §7

## Context

ADR-0006 made the lane confidential but left the keys without a source:
`TunnelCipher` takes a 32-byte key and a 3-byte salt and nothing in the product
could produce them. §9.2 states the requirement directly — "keys rotate per
session with forward secrecy (Noise-style handshake)" and "client verifies relay
identity key pinned at provisioning" — so the missing piece is key agreement,
not more crypto primitives.

## Decision

**1. `Noise_IK_25519_ChaChaPoly_BLAKE2s`, implemented first-party.**
The blueprint splits the work exactly this way: "first-party Noise-style
handshake" over "vendored, pinned, audited" primitives (§4.8 component table).
`IK` is the pattern the product's trust model implies — the client pins the
relay's static key at provisioning, which *is* `IK`'s pre-message — and it
completes in two flights:

```text
<- s                     (pinned at provisioning)
-> e, es, s, ss          initiator authenticates, forward secrecy established
<- e, ee, se             responder replies; both sides Split() into transport keys
```

**2. Three more pinned primitives, all from the same allowlist discipline.**
`x25519-dalek =2.0.1` (BSD-3-Clause, `static_secrets` so a key can be built from
stored bytes), `blake2 =0.10.6`, `hkdf =0.12.4`. Four pinned crates is now the
whole third-party surface, each enforced by `tools/ci/audit-deps.sh`.

**3. Secrets are arguments, not side effects.**
Every secret — static *and* ephemeral — enters as a `[u8; 32]` parameter. That
keeps the module sans-I/O like the rest of the core, makes the tests fully
deterministic with no RNG in the dependency tree, and puts key storage where
§9.2 puts it: the service sources static keys from DPAPI/TPM and ephemeral bytes
from the platform CSPRNG.

**4. The handshake hash is the tunnel's nonce salt.**
`TransportKeys::salt()` takes the first three bytes of the handshake hash
(`GetHandshakeHash()`, spec §11.2 channel binding). Transport nonces are
therefore bound to the transcript, so two sessions that somehow shared a key
would still not share a nonce — and the two directions use different keys
anyway, from `Split()`.

**5. Followed the specification text, not a recollection.**
`SymmetricState` (`MixKey`, `MixHash`, `EncryptAndHash`, `DecryptAndHash`,
`Split`) and the `IK` token rules were read out of the Noise specification while
writing this. One correction came out of that: `MixKeyAndHash` is *not* part of
plain `IK` — the specification reserves it for the `psk` modifier.

**6. Reject non-contributory X25519 terms.** Every DH operation checks the
`SharedSecret::was_contributory()` result supplied by the pinned X25519 library
and returns `AuthFailed` for an all-zero shared secret. Initiator flight 1 now
returns a `Result` so a bad pinned relay key fails before a frame is emitted;
inbound and responder-flight paths likewise validate all DH terms before
advancing the transcript. A low-order peer static discovered after its encrypted
flight field is decrypted poisons that responder instance rather than allowing
reuse of a partially advanced transcript. Regression tests cover low-order
static and ephemeral values. Hosted validation is tracked in the completion
ledger.

## Known gap: no conformance vectors

The official Noise test vectors are generated by the reference tools and are not
committed to the specification repository, and the hosts that serve them are not
reachable from this environment. **The tests therefore prove that two of our
peers agree, authenticate, and reject tampering — not that we are byte-for-byte
compatible with another Noise implementation.** Interop against `snow` (or the
spec's JSON vectors) is a required follow-up before this handshake can be called
conformant, and it is the first thing to run once a toolchain is available.

## Rejected

- **`Noise_XX`** — mutual authentication without a pinned key, at the cost of a
  third flight and a TOFU decision we do not have to make: the relay's identity
  is already pinned at provisioning.
- **`Noise_NN`** — no authentication at all; fails §9.2 outright.
- **A `psk` pattern** — would make the handshake depend on a shared secret
  instead of an identity, and PSKs do not give forward secrecy on their own.
- **Our own X25519** — forbidden by §4.8 ("never roll our own primitives").

## Consequences

- The responder learns the initiator's static key from flight 1
  (`Responder::peer_static()`), so relays can pin clients on the same mechanism
  clients use to pin relays.
- Flights are ordered and length-checked: out-of-order use is `BadOrder`, short
  messages are `Truncated`, and nothing is parsed before it is verified.
- **Still missing:** key storage and rotation (DPAPI/TPM, `Rekey()` after N
  frames), a session-table integration so `auto_accept` can default to false,
  and a replay cache for first flights. Those are the next increment, not this
  one.
